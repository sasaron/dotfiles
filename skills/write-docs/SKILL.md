# ドキュメントを作成・更新する

依頼された読者と目的に合わせて、必要な情報を探しやすく、事実と判断の根拠が
分かる文書にする。ユーザーの指定とプロジェクトの指示・既存書式を優先する。
WordやPDFなどの形式に専用の作成手順がある場合は、併用する。

## 作業の進め方

1. 対象、目的、読者、納品形式を把握する。`AGENTS.md`や`CLAUDE.md`、既存の
   文書・テンプレート・配置規則を確認し、明示されていない部分は周辺に合わせる。
   詳細が未指定なら、既存構成を踏まえて妥当な範囲で進める。
2. リポジトリ内の関連コード、設定、既存資料を調べ、事実と提案・未決事項を区別する。
   外部仕様やバージョンに依存する主張は必要に応じて公式資料などの一次情報で確認し、
   根拠へのリンク、対象の版や確認条件を読者が追える形で記載する。
   不明な点は推測で断定せず、判断に必要な情報とともに明示する。
3. 文書の種類と規模に応じて構成を選ぶ。既存資料と重複する情報は参照し、
   変更が関連資料に影響する場合は、必要な範囲でリンクや案内も更新する。
4. 文章、リンク、コマンド、図や表の整合性を確認する。実行を伴う手順は、
   適切な環境で検証するか、未検証であることを明記する。

## 文書の構成

- README・利用ガイド：対象と用途、前提条件、始め方、よく使う操作を示す。
  リポジトリ固有のコマンドやパスは実際の構成と照合する。
- 設計書・仕様書：背景、目的と対象範囲、制約、構成や振る舞い、
  判断と理由、リスク・未決事項、検証方法から、対象に必要なものを選ぶ。
  インターフェース、状態遷移、データ、失敗時の扱いは設計に必要な場合に記す。
- 運用・作業手順：前提権限や環境、実行順、期待する結果、失敗時の確認・復旧を
  必要に応じて記す。読者が操作対象を識別できる具体例を使う。
- その他の文書：読者の必要とする判断・行動に応じて構成する。
  不要な見出しやプロジェクト固有の設計様式を機械的に追加しない。

## 書き方

- 内容のまとまりは適切な階層の見出し（`##`、`###`、`####` など）と段落で整理する。
  見出しの階層は文書全体で一貫させ、意味のない小見出しを増やさない。
- 見出しや本文で太字・斜体などの強調表現を使わない。重要な点は言葉と構成で示す。
  コード、コマンド、リンクは用途に応じた書式を使う。
- 文書の冒頭から順に読んで目的と意図が伝わるように、背景・目的・結論・理由・
  必要な行動を適切な順序でつなぐ。後の節で初めて説明される前提に依存しない。
- 各節の結論を先に置き、読者が理由や次の行動を追えるように書く。
- 長さと詳細を目的に合わせ、用語は初出時に必要なら説明する。
  文書の言語・表記はユーザーの指定や既存資料に合わせる。
- 手順は順序付きリスト、比較や項目対応は表、複雑な関係は図など、
  内容を分かりやすくする形式を選ぶ。形式や図の数を一律に決めない。
- 数字は実測値・出典・概算の別を示し、存在しない操作やファイルを作らない。
  情報が確認できない場合や環境によって変わる場合は、その条件を記す。
- 資料には読み手に必要な情報を残す。コード、ログ、コマンド例、履歴や
  トラブルシューティングも、文書の目的に必要なら適切な範囲で含める。
- セキュリティ上の機密、個人情報や端末固有の値は、公開先と用途に応じて扱う。

## 完了前の確認

- 読者が目的を達成するための前提・手順・期待結果が分かるか。
- 記述は実装、対象バージョン、関連文書と一致するか。未確認事項を区別したか。
- 上から読んで意図と判断の流れが伝わり、前提のない説明がないか。
- 見出しの階層が適切で、太字・斜体などの強調表現を使っていないか。
- 見出し、リンク、コードブロック、図表は正しく表示されるか。
- 変更範囲に応じた検証を行い、実行できなかった確認を報告したか。

コミットや外部への公開・投稿は、ユーザーが依頼または許可した範囲で行う。
